Axios Refresh-Token Interceptor

Client-side companion to authentication. When the API returns 401 (access token expired), the interceptor transparently calls /auth/refresh and retries the original request — once.

Overview

On the client, token expiry should be invisible to app code. Instead of every call site handling 401s, one Axios response interceptor:

  1. Catches a 401 from any request.
  2. Calls POST /auth/refresh once (single-flight).
  3. On success, retries the failed request (and any others that 401’d during the refresh).
  4. On failure, clears the session and redirects to login.

Stack-specific. Code below is Axios + TypeScript (browser). The pattern ports to fetch wrappers, TanStack Query retry, SWR, or native mobile HTTP clients — the single-flight + queue logic is the same.

How it works (single-flight + queue)

The critical part is not the refresh call — it’s preventing a refresh storm. When the access token expires, many in-flight requests fail with 401 at once. Naively, each would trigger its own refresh → multiple parallel /auth/refresh calls → rotation thrash and possible family revocation on the server.

The fix: one refresh at a time, others wait.

sequenceDiagram
  autonumber
  participant App as App code
  participant Int as Axios interceptor
  participant API as API server
  App->>Int: GET /orders (access cookie)
  Int->>API: request
  API-->>Int: 401 (access expired)
  Note over Int: not refreshing yet -> start refresh
  Int->>API: POST /auth/refresh (refresh cookie)
  Note over Int: other 401s arrive -> queued on the same refresh promise
  API-->>Int: 200 (new access cookie set)
  Note over Int: replay original + queued requests
  Int->>API: GET /orders (new access cookie)
  API-->>Int: 200
  Int-->>App: resolved

The decision each 401’d request makes, and how a single refresh + queue handles all of them — including failure:

flowchart TD
  R1["Request 1 gets 401"]
  R2["Request 2 gets 401"]
  R3["Request 3 gets 401"]
  R1 --> CHK{"refresh already running?"}
  R2 --> CHK
  R3 --> CHK
  CHK -->|"no, first one in"| START["start the single refresh"]
  CHK -->|"yes, the others"| WAIT["wait on the same refresh"]
  START --> RESULT{"refresh result"}
  RESULT -->|"200 new tokens"| SUCC["refresh succeeded"]
  RESULT -->|"401 token dead"| DEAD["refresh failed, handleSessionExpired"]
  RESULT -->|"network or 5xx"| BLIP["refresh failed, keep session"]
  WAIT -.->|"resolves on"| SUCC
  WAIT -.->|"resolves on"| DEAD
  SUCC --> REPLAY["replay 1, 2, 3 with fresh credentials"]
  DEAD --> CLEAR["1, 2, 3 rejected; redirect to login once"]

Read it as: the first 401 to arrive starts the only refresh; every other concurrent 401 waits on that same refresh. On success they all replay; on a dead refresh token they all reject and the user is sent to login exactly once. A transient error rejects them too but keeps the session.

Cookie-based vs header-based

Auth style Access token transport Refresh response Interceptor must…
HttpOnly cookie (this design) Sent automatically New cookies set by Set-Cookie withCredentials: true; nothing to attach on retry
Bearer header Authorization: Bearer { accessToken, refreshToken } in body Store new token, attach on replay

The logic below handles both — the header path is commented.

Implementation

import axios, { AxiosError, type InternalAxiosRequestConfig } from 'axios';

type Retriable = InternalAxiosRequestConfig & { _retry?: boolean };

const api = axios.create({
  baseURL: import.meta.env.VITE_API_URL ?? '/api',
  withCredentials: true, // send the HttpOnly auth cookies
});

// --- single-flight refresh (same tab + across tabs) -------------------------
// One in-flight refresh at a time WITHIN a tab: every concurrent 401 awaits the
// SAME promise. AND one refresh at a time ACROSS tabs: navigator.locks holds a
// single origin-wide lock, so two tabs sharing one refresh cookie can never both
// POST /auth/refresh at once — the server would read the second as token reuse
// and revoke the family (see Authentication).
let refreshPromise: Promise<void> | null = null;

function isAuthGone(e: unknown) {
  return Boolean((e as any)?.response?.status === 401); // token dead, not a blip
}

function doRefresh(): Promise<void> {
  // Use `api` (not bare `axios`) so the request uses the same baseURL.
  // The isRefreshCall guard below prevents the interceptor from recursing.
  return api
    .post('/auth/refresh', {}, { withCredentials: true })
    .catch((e) => {
      if (isAuthGone(e)) handleSessionExpired();        // see "When refresh fails"
      throw e;                                          // reject every awaiter
    });
}

function refresh(): Promise<void> {
  if (refreshPromise) return refreshPromise;            // join the in-flight refresh

  refreshPromise = (async () => {
    if (navigator.locks) {
      // Serialize across tabs: only one holder of 'auth-refresh' per origin.
      await navigator.locks.request('auth-refresh', () => doRefresh());
    } else {
      await doRefresh(); // no Web Locks API (old browsers): same-tab single-flight only
    }
  })().finally(() => {
    refreshPromise = null;                              // let the next 401 start fresh
  });

  return refreshPromise;
}

// --- request interceptor: attach Bearer token only if header-based ---------
api.interceptors.request.use((config) => {
  // const token = getAccessToken();                       // header-based only
  // if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

// --- response interceptor: catch 401, refresh once, retry -------------------
api.interceptors.response.use(
  (res) => res,
  async (error: AxiosError) => {
    const original = error.config as Retriable | undefined;

    const expired = error.response?.status === 401;
    const retried = original?._retry === true;
    const isRefreshCall = original?.url === '/auth/refresh'; // exact, not substring

    if (!expired || !original || retried || isRefreshCall) {
      return Promise.reject(error); // not a refreshable 401
    }

    original._retry = true;          // guard against retry loops on every replay
    try {
      await refresh();               // single-flight: many 401s share this promise
      return api(original);          // replay with fresh credentials
    } catch {
      return Promise.reject(error);  // refresh failed -> propagate the original 401
    }
  },
);

export default api;

// handleSessionExpired() is defined in "When refresh fails".

Why this is race-safe (browser JS)

Browser JavaScript is single-threaded: one call stack, one event loop. A function runs to completion — it is never paused mid-statement so another function can run. Control can switch to another task only at yield points: await, promise callbacks, timers, and event handlers. Between yield points, synchronous code is atomic.

That redefines “race condition.” In a multi-threaded language (Java, Go, C++), two threads can both read a flag as false before either sets it true, starting two refreshes — you’d need a mutex. In JS that cannot happen as long as the check and the write have no await between them.

In refresh() they don’t:

function refresh() {
  if (refreshPromise) return refreshPromise;   // read
  refreshPromise = (async () => { /* ... */ })();   // write — no await in between
  return refreshPromise;
}

Read-then-write is one atomic synchronous block. Request B’s refresh() cannot run between A’s check and A’s assignment, because A hasn’t yielded. So at most one refresh promise is ever created. ✅

The rule is simple: keep shared-state read + write on the same side of an await. If you ever await between reading a flag and acting on it, another task can change it under you — that is where JS “races” actually live.

Scope: the per-realm refreshPromise makes a single tab race-safe. Cross-tab refresh must be serialized too — two tabs share one refresh cookie, so if both POST /auth/refresh concurrently the server reads the second as token reuse and revokes the family (see Authentication). navigator.locks.request('auth-refresh', …) holds one refresh per origin at a time, so tabs refresh in sequence, never in parallel. Browsers without the Web Locks API fall back to same-tab single-flight only, where genuine multi-tab use can still trip server-side reuse detection. True parallelism — Web Workers sharing SharedArrayBuffer — would need its own synchronization on top.

Usage

App code never handles 401 — the interceptor makes expiry transparent:

import api from './api';

// these just work; if the access token expired, the interceptor refreshes and retries once
const { data: me } = await api.get('/auth/me');
const { data } = await api.get('/orders', { params: { page: 1 } });
await api.post('/orders', { items: [...] });

If a call still rejects after that, the request genuinely failed — a non-401 error, or a 401 that persisted past refresh (session dead). Handle that at the call site or a global error boundary, not by re-authenticating.

When refresh fails (session expired)

Refresh failure has two causes — handle them differently:

Cause Signal Action
Refresh token dead (expired / revoked / reused / missing) POST /auth/refresh returns 401 (e.g. REFRESH_REVOKED) End the session: clear state, notify UI, redirect to login
Transient (network blip / 5xx) refresh errors with no 401 Propagate; do not log out — the session may still be valid

Distinguish by status, not by “refresh threw”:

const isAuthGone = (e: any) => e?.response?.status === 401;

The failure flow — and how a dead token differs from a transient blip:

Session-expired handler (idempotent)

Several requests can fail-refresh at once — the handler must fire once:

// auth-events.ts — decouple the interceptor from UI (no import cycles)
type AuthListener = (reason: 'session-expired') => void;
const listeners = new Set<AuthListener>();
export const authEvents = {
  on: (l: AuthListener) => { listeners.add(l); return () => { listeners.delete(l); }; },
  emit: (r: 'session-expired') => listeners.forEach((l) => l(r)),
};

let sessionDead = false;                       // latch
export function handleSessionExpired() {
  if (sessionDead) return;                     // one event, one redirect
  sessionDead = true;

  clearStoredAuth();                           // header-based: drop stored tokens; cookie-based: clear in-memory user

  authEvents.emit('session-expired');          // let the UI react

  const ret = encodeURIComponent(location.pathname + location.search + location.hash);
  location.assign(`/login?redirect_url=${ret}`);  // preserve where the user was
}

UI reaction (example: React + TanStack Query)

useEffect(() => authEvents.on(() => {
  queryClient.clear();                         // drop data tied to the dead session
  toast.error('Your session has expired. Please sign in again.');
}), []);

Wiring

The interceptor’s catch (see Implementation) calls it once:

if (isAuthGone(refreshError)) handleSessionExpired();

Notes

  • Idempotency matters. Without the sessionDead latch, ten failing requests fire ten redirects/toasts.
  • Cookie-based logout. Optionally call POST /auth/logout before redirecting so the server revokes the family and clears cookies at once; tolerate failure — the token may already be revoked.
  • Don’t yank the user on background polls. For low-priority background calls, prefer a non-blocking “session expired” banner over a hard mid-task redirect.
  • Never treat a transient network error as logout. A offline refresh is not a dead session — the user is still authenticated; surface it as a transient error, or retry.

Key decisions

  • Single-flight (one shared refresh promise). Exactly one /auth/refresh runs; concurrent 401s await the same promise instead of re-triggering it. This also protects the server’s rotation/family logic from parallel refreshes.
  • _retry flag. Marks a request already retried so a second 401 after refresh propagates instead of looping forever.
  • Skip the refresh call itself. A 401 from /auth/refresh means the refresh token is dead → reject, do not recurse.
  • Replay queue. Requests that 401’d while refreshing resolve off the same refresh promise, then replay with the fresh credentials.
  • Fail closed. Refresh failure clears state and redirects; queued requests are rejected, not left hanging.

Pitfalls

  • Infinite loop. Always set _retry and never intercept the /auth/refresh call. Missing either → retry → 401 → retry → forever.
  • Refresh storms. Without single-flight, N concurrent expired requests fire N refreshes → server rotates the family N times → possible reuse-detection false positive / revocation.
  • Replay with a stale token (header-based). Ensure the new access token is in storage before replaying; otherwise the retried request uses the old token and 401s again.
  • Refreshing on non-401. Only act on 401. A 403 (forbidden) or network error must not trigger a refresh.
  • Forgetting withCredentials. Without it, the browser won’t send the HttpOnly auth cookies, so every request 401s — including the refresh.
  • Refresh call bypassing baseURL. Don’t call bare axios.post('/auth/refresh') — it has no baseURL, so with baseURL: '/api' it hits /auth/refresh (404) instead of /api/auth/refresh. Use api.post(...); the isRefreshCall guard already stops the interceptor recursing on its own 401.
  • Substring recursion guard. url.includes('/auth/refresh') also matches /auth/refresh-log. Compare exactly (url === '/auth/refresh') or tag the refresh request with a config flag.
  • Replaying consumed bodies. api(error.config) is safe for JSON, but FormData / streams / file uploads may already be consumed → the replay sends an empty body. Rebuild the body for upload routes.

Notes

  • Pair with a route guard / app bootstrap that loads /auth/me once on startup so the app knows the initial auth state before rendering.
  • If you also use TanStack Query, you can centralize this in a query retry function instead of an Axios interceptor — but the single-flight + queue logic is identical.
  • For server-side rendering (Next.js, Nuxt), refresh must run on the server too; reuse the same cookie jar across the boundary.
